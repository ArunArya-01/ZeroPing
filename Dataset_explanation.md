# AeroTwin Featured Dataset Explanation

## Overview

This document explains the `featured_dataset.parquet` file, which is the training-ready dataset for the hybrid physics + ML model (AeroTwin).

**Purpose**: Each row represents one **labeled fuel interval** from the EUROCONTROL PRC 2025 challenge data. The dataset combines:
- Raw flight trajectories (ADS-B + ACARS)
- Fuel consumption labels (derived from ACARS fuel-on-board differences)
- Physics baseline predictions from OpenAP

The goal is to train a **residual model** that learns to correct the OpenAP physics predictions (`physics_fuel_kg`) to match the actual observed fuel burn (`actual_fuel_kg`).

The key target for the ML model is often the **residual**:
```python
residual_kg = actual_fuel_kg - physics_fuel_kg
```

## How the Dataset Was Built

The dataset is generated by `physics/build_featured_dataset.py`:

1. Uses `data.AeroDataLoader` to access the remote Hugging Face dataset (`aerotwin/aero-data`) without downloading everything.
2. Gets the list of **usable flights** (those with both flightlist metadata + trajectory parquet files). There are ~10,000 usable flights in the train split (out of 11,037 total).
3. For each usable flight:
   - Loads the full trajectory (time-series of lat/lon/alt/speed/etc. fused from ADS-B and ACARS).
   - Loads the corresponding fuel labels for that flight (multiple intervals per flight).
   - Loads flight metadata (aircraft_type, origin, destination, takeoff/landed times).
   - Calls `physics.openap_baseline.predict_fuel_intervals(...)` which:
     - Matches trajectory points to each fuel interval [start, end].
     - Computes OpenAP physics fuel prediction for the interval (using TAS inference from available mach/CAS/groundspeed, reference mass, etc.).
     - Extracts rich per-interval features from the window of trajectory points.
4. Computes `residual_kg`.
5. Concatenates everything into one big Polars DataFrame and writes `featured_dataset.parquet`.

**Important notes on scale**:
- Full run processes 10,000 flights → ~110k–120k rows (one per fuel interval).
- It is slow because it does many remote loads over the network.
- The script supports a limit: `python -u physics\build_featured_dataset.py 500` for testing.
- Progress is printed every 20 flights.

The builder also ensures the path hack so it can be run from outside the project directory.

## Dataset Schema and Columns

The parquet has 31 columns (some are "debug" columns kept for traceability).

### Target
- `actual_fuel_kg` (Float64): The ground-truth fuel burned in this interval (from ACARS FOB diffs). **This is the primary label.**

### Physics Baseline
- `physics_fuel_kg` (Float64): OpenAP-predicted fuel for the interval.
- `residual_kg` (Float64): `actual_fuel_kg - physics_fuel_kg`. Positive = physics under-predicted; negative = over-predicted. This is often the thing the neural net is trained to predict.

### Flight Metadata
- `aircraft_type` (String): e.g., "A20N", "B789", "A359". One of 26 types in the data. A320 family dominates.
- `origin_icao` (String)
- `destination_icao` (String)

### Interval Metadata
- `duration_s` (Float64): Length of the fuel label interval in seconds (typically 300–3600s after filtering).
- `start_fraction_of_flight` (Float64): 0.0 to 1.0 — where this interval starts relative to the full takeoff→landed duration.
- `end_fraction_of_flight` (Float64): Same for the end of the interval.

### Trajectory Quality / Observability
- `n_traj_pts` (Int64): Number of trajectory points falling inside this fuel interval. 
  - Many intervals have very few points (2-pt = just the bounding ACARS reports).
  - This is one of the most important signals discovered in EDA.
- `has_acars_in_window` (Boolean): Whether any ACARS-sourced points are inside the interval.

### Altitude Features (computed over the window of traj points in the interval)
- `mean_altitude`, `median_altitude`, `max_altitude`, `std_altitude` (all Float64, in meters)

### Speed Features
- `mean_groundspeed`, `std_groundspeed`, `max_groundspeed` (Float64, m/s)

### Vertical Rate Features
- `mean_vertical_rate`, `std_vertical_rate` (Float64, m/s)

### Phase Features (fraction of points in the window classified by vertical rate)
- `climb_fraction`, `cruise_fraction`, `descent_fraction` (Float64, 0–1)
  - Simple rule: vr > +1.5 m/s → climb, vr < -1.5 → descent, else cruise.
  - These capture the flight phase context within the fuel interval.

### Telemetry / Physics Method
- `method` (String): How the OpenAP baseline obtained TAS for the prediction:
  - `tas_from_mach`
  - `tas_from_cas`
  - `tas_from_gs` (fallback when no air data)
  - `fallback_tas_200`
  - `..._short` variants (for very short intervals)
  - `no_coverage`

### Debug / Traceability Columns (kept for now)
- `interval_idx`, `start`, `end` (the original fuel label times)
- `tas_used`, `alt_used`, `vs_used` (the representative values fed to OpenAP)
- `phase` (the single dominant phase for the interval, for compatibility with older analysis)

## Key Insights from EDA (reflected in this dataset)

From the full EDA work (see `notebooks/` scripts and the complete summary notebook):

- **Partial observability**: Labels only cover a fraction of most flights (median ~32% of takeoff-to-landed time). Many long-haul flights only have labels on the later part of the trip.
- **Extreme heterogeneity in data quality**: ~35–46% of intervals are "very sparse" (<5 traj points). The residual model must be robust to this.
- **Source-dependent features**: Only ACARS rows ever have mach/TAS/CAS. ADS-B is dense but provides only kinematics + nulls for air data.
- **Physics is biased**: On real data, OpenAP (with simple reference mass) tends to over-predict fuel on many intervals, especially cruise and when using fallbacks.
- **Residuals are learnable but structured**: Errors correlate with duration, phase, sparsity, aircraft type, and whether real ACARS air data was available.
- **Aircraft type matters a lot**: Wide-bodies (A359, B789, etc.) have very different fuel scales and error patterns than narrow-bodies.

The columns in this parquet were explicitly chosen to let a neural net see these signals (n_traj_pts, has_acars, phase fractions, aircraft_type, fractions of flight, altitude/speed stats, etc.).

## How to Use for Modeling

Typical setup for the residual model:

```python
import polars as pl
import torch
from torch.utils.data import Dataset, DataLoader

df = pl.read_parquet("featured_dataset.parquet")

# Features (example — expand as needed)
feature_cols = [
    "physics_fuel_kg",           # strong baseline
    "duration_s", "start_fraction_of_flight", "end_fraction_of_flight",
    "n_traj_pts", "has_acars_in_window",
    "mean_altitude", "std_altitude",
    "mean_groundspeed", "std_groundspeed",
    "mean_vertical_rate", "std_vertical_rate",
    "climb_fraction", "cruise_fraction", "descent_fraction",
]

# Categorical
df = df.with_columns(
    pl.col("aircraft_type").cast(pl.Categorical).to_physical().alias("aircraft_type_idx"),
    pl.col("method").cast(pl.Categorical).to_physical().alias("method_idx"),
)

# Target — you can train on residual or on actual (with physics as feature)
target = df["residual_kg"].to_numpy()   # or df["actual_fuel_kg"]

# Later: embeddings for aircraft_type_idx + method_idx, etc.
```

Common modeling choices:
- Train the net to predict `residual_kg`. Final prediction = physics + predicted_residual.
- Or train to predict `actual_fuel_kg` while including `physics_fuel_kg` as a strong feature (the net learns the correction implicitly).
- Weight samples by `1 / (n_traj_pts + 1)` or similar because sparse intervals are noisier.
- Use the phase fractions and sparsity flags as explicit features or for conditional modeling.

## Limitations & Gotchas

- The full parquet is large (tens of MB). For quick experiments use a subset (the builder supports it).
- Some intervals have `physics_fuel_kg = null` (no_coverage cases) — handle them (drop or special mask).
- `origin_icao` / `destination_icao` are strings — you will probably want to embed or one-hot the common ones.
- The data is **not** i.i.d. across rows (multiple intervals from the same flight are correlated). Consider flight-level splitting for train/val.
- OpenAP baseline used a simple reference mass (mtow * 0.75). A better mass estimator (or learning mass as latent) is future work.
- The dataset reflects the realities of the original challenge data (gaps, source mixing, partial labels).
